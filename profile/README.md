<h2>网络层四步走</h2>
<h3>第一步：地址落到网卡</h3>
<p>地址、掩码、网关三项必须成对使用。掩码写小会把外网当内网，写大会把可用地址压掉。配完立刻验证：查看默认路由的下一跳是否等于交付网关，这是最直接的判断。若服务方给的是通过代理方式提供的住宅地址，则不需要配到网卡上，直接进入第三步的转发配置。</p>
<h3>第二步：DNS 与解析</h3>
<p>两个地址即可，一个主用一个备用，选择与出口同区域的公共解析。改完用解析回显页确认实际解析地，不要只看配置文件。解析地与出口不同区，是很多「明明配好了还是异常」的根源。</p>
<h3>第三步：转发与出口</h3>
<p>如果由服务器内的程序经住宅地址出去，需要在服务器上运行客户端并把本地端口暴露给浏览器。注意监听范围：只监听本机回环，不要监听全部网卡，否则这个端口会变成公网可用的开放代理，被人扫到之后你的地址会被陌生流量污染。</p>
<h3>第四步：防火墙收敛</h3>
<p>默认拒绝入站，只放行管理与业务所需端口。远程管理端口建议改到非默认值并限制来源地址，业务端口按需开放。这一步不是可选项——暴露在公网的服务器平均几小时内就会收到扫描。</p>

<h2>系统层面的三项优化</h2>
<p>其一，关闭不需要的服务。系统默认会跑一堆用不到的组件，既占资源也增加攻击面。其二，时间同步。时序错乱会导致证书校验失败、日志无法对齐，排查故障时非常难受。其三，日志留存。至少保留七天的网络与服务日志，出问题时能还原当时的情况。</p>
<p>这三项改动都很小，但对长期稳定运行的影响远大于折腾各种性能参数。</p>

<h2>验收：不只看能不能打开网页</h2>
<p>验收要能回答四个问题：出口地址是否符合预期、解析是否与出口同区、端口是否只开了该开的、连续运行是否稳定。前三个当场可测，第四个需要观察一段时间。</p>
<p>做法是跑一个持续一段时间的小任务，例如每分钟访问一次回显接口并记录结果，跑满二十四小时看曲线。曲线平稳说明链路可用；出现规律性掉线，多半是服务端限速或链路拥塞；出现随机断流，则要检查 MTU 与会话数上限。</p>

<h2>常见故障的定位顺序</h2>
<p>页面打不开时，按「本机出网—代理链路—解析—目标站点」的顺序逐段验证。本机出网用 ping 网关与外部地址；代理链路用回显接口；解析用解析回显页；最后才测目标站点。跳过前面直接测目标站点，只会得到一个「不行」的结论，得不到原因。</p>
<p>另一个高频问题是「时快时慢」。先看是不是晚高峰，再看是不是并发过高，最后看 MTU。这三个原因的处理方式完全不同，不要一律归咎于服务商。</p>

<h2>常见问答</h2>
<h3>搭建需要多长时间</h3>
<p>环境配置本身通常一两个小时能完成，真正耗时的是验收与观察。建议留出一天做连通测试，再用几天观察稳定性，不要当天上线当天压业务。</p>
<h3>必须用独立服务器吗</h3>
<p>不必。单身份场景用一台轻量机器即可，多人协作才需要更完整的方案。先用最小可行配置跑通，再按需扩容，比一次买顶配更划算。</p>
<h3>地址是住宅的，还需要额外配置吗</h3>
<p>需要。地址只决定来源，解析、时区、语言、浏览器环境仍要各自配置并保持一致。只换地址不改环境，等于半套。</p>
<h3>自建和买现成服务哪个好</h3>
<p>有运维能力时自建更可控，参数透明、可以按需调整；没有运维能力时，选能提供部署与巡检的服务更省事。两种方式都要保留验收环节。</p>
